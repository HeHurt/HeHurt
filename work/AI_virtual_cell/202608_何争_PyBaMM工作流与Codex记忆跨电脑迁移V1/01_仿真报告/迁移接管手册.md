# PyBaMM与Codex记忆迁移接管手册

## 1. 推荐复制顺序

1. 关闭旧电脑上的 Codex、VS Code、Jupyter、Python、COMSOL 和 MATLAB。
2. 复制真实工作区 `C:\HithiumSSD\hithium`，不要把 junction `D:\Users\hez\Desktop\hithium` 当成第二份数据。
3. 将本任务包单独保存到移动硬盘、NAS 或另一份校验过的备份中。
4. 在新电脑先安装 Codex 和 Python，再恢复项目与长期记忆。
5. 保留旧电脑，直到新电脑复现至少一个历史 PyBaMM 任务。

## 2. 恢复长期记忆

1. 在新电脑启动一次 Codex 后退出。
2. 确认新电脑的 Codex home，默认是 `%USERPROFILE%\.codex`。
3. 如果新电脑已有 `memories`，先将其改名备份，不要直接覆盖。
4. 解压 `Codex_long_term_memories_complete.zip`，把其中的 `memories` 放到新电脑 Codex home 下。
5. 把 `03_输入数据/memory_config_template.toml` 的内容合并进新电脑 `config.toml`。
6. 重启 Codex，使用 `/memories` 确认当前任务允许使用和生成记忆。

`codex_memory_tree/memories` 是同一记忆快照的展开镜像，供人工检查和应急恢复；不要同时导入两份。

## 3. 历史 sessions 的定位

`Codex_historical_sessions_evidence.zip` 是历史证据包，不是长期记忆包。它用于找回：

- 未被后台提炼进 memory 的细节；
- 精确命令、报错、时间和工具输出；
- 已归档任务的原始上下文；
- automation 的历史状态。

不要直接用该压缩包覆盖新电脑的整个 `.codex`。当前 Codex 没有承诺手工复制 sessions 后一定恢复侧边栏任务；应把它作为只读证据库，通过 `session_index.jsonl`、thread id 或 memory 中记录的 `rollout_path` 定位。

## 4. 项目接管资产

除本任务包外，新电脑还必须拥有完整工作区，特别是：

```text
.git/
AGENTS.md
BatteryProject/src/
BatteryProject/tests/
BatteryProject/examples/
BatteryProject/output/runs/
params/
data_raw/
data_processed/
datasets.json
work/
tools/
skills/
```

仅从 GitHub clone 不足以恢复实验数据、Notebook、运行结果和未提交修改。

## 5. Skills 与路径

新电脑需要让 `%USERPROFILE%\.codex\skills` 指向新工作区的 `skills` 真源。建立 junction 前先确认目标不存在或已经完成备份。随后检查脚本中的旧绝对路径：

```text
C:\HithiumSSD\hithium
D:\Users\hez\Desktop\hithium
C:\Users\hez
D:\软件安装\Microsoft VS Code\Code.exe
```

## 6. 环境与验收

在旧环境导出 `python -m pip freeze`；新电脑按原版本重建，不直接升级 PyBaMM。最低验收包括：

1. Git branch、HEAD 和 dirty 状态与迁移快照一致。
2. Codex 能读取根目录及嵌套 `AGENTS.md`。
3. `/memories` 已启用，能检索 `MEMORY.md` 中的 Hithium/PyBaMM 条目。
4. 项目 Skills 可被发现。
5. `datasets.json` 指向的数据文件存在。
6. 参数函数能返回 `Nominal cell capacity [A.h]`。
7. 单温度、单 SOC、单循环 smoke test 成功。
8. 至少一个历史任务包的关键指标与旧电脑一致。

## 7. 安全边界

- 记忆可能包含公司项目上下文，只使用合规介质迁移。
- 新电脑必须具备相同 DLP 解密条件，否则 `%TSD-Header-###%` 文件可能无法使用。
- 不复制 auth、token 或整个 `.codex` 覆盖新环境。
- 哈希一致只证明字节一致，不证明 DLP 解密链、Python环境或仿真结果已经可用。
